## 3. Архитектура


Схема развёртывания: пользователи по HTTP попадают в AWS Cloud (eu-central-1, default VPC, зона доступности, подсеть, Security Group) на экземпляр EC2 с nginx, PHP-FPM и PostgreSQL. Сервер забирает код с GitHub по HTTPS, а с моего компьютера выполняются `git push` и запуск деплоя по SSH.

## 4. Ответы на вопросы из заданий

**Задание 1. Что разрешает AdministratorAccess? Почему нельзя использовать root?**
AdministratorAccess даёт полный доступ ко всем сервисам и ресурсам аккаунта AWS, кроме действий, доступных только root (например, закрытие аккаунта и смена плана поддержки). Root нельзя использовать в повседневной работе, потому что у него неограниченные права и его нельзя урезать политиками. Утечка его пароля или ключей означает полную потерю контроля над аккаунтом, а IAM-пользователя можно ограничить, отозвать или удалить.

**Задание 2. Что такое User data и когда выполняется?**
User data — это скрипт, который передаётся экземпляру при запуске и выполняется cloud-init от имени root. По умолчанию он выполняется только один раз, при первом запуске. После перезагрузки или остановки и запуска скрипт повторно не выполняется.

**Задание 3. Какая проверка указывает на проблему, которую можете исправить вы, а какая — на сторону AWS?**
System status check показывает проблемы инфраструктуры AWS (сервер, сеть, питание), их решает AWS, а мне остаётся остановить и запустить экземпляр, чтобы он переехал на другой хост. Instance status check показывает проблемы внутри ВМ (ядро, сеть ОС, неверная конфигурация), и их исправляю я. Attached EBS check относится к доступности дисков.

**Задание 3. Когда включать детальный мониторинг?**
Детальный мониторинг (метрики раз в минуту) нужен для продакшена и критичных сервисов, где важно быстро заметить всплеск нагрузки, для настройки аварийных сигналов с быстрой реакцией и для автомасштабирования. Для учебного сервера хватает базового мониторинга, детальный стоит дополнительных денег.

**Задание 4. Почему для входа используется ключ, а не пароль?**
Приватный ключ не передаётся по сети и практически не поддаётся подбору, в отличие от пароля, который можно угадать или перебрать. Сервер хранит только публичный ключ, поэтому его утечка не раскрывает доступ. Вход по паролю на публичных серверах постоянно атакуется ботами.

**Задание 5. Что делает scp и чем похожа на ssh?**
scp копирует файлы между компьютером и сервером по защищённому каналу. Она использует тот же протокол SSH, те же ключи, порт 22 и ту же аутентификацию, поэтому параметры `-i` и `user@host` у неё такие же, как у ssh.

**Задание 6. Чем Stop отличается от Terminate? За что платим при остановке?**
Stop останавливает экземпляр, но сохраняет его и диск EBS, и его можно запустить снова (публичный IP при этом меняется). Terminate удаляет экземпляр навсегда, а корневой диск по умолчанию удаляется вместе с ним. Пока экземпляр остановлен, вычислительная часть (t3.micro) не тарифицируется, но платить продолжаем за EBS-тома и, например, за Elastic IP.

**Задание 7. Почему vendor/ и .env не попали в репозиторий?**
Они указаны в `.gitignore`. В `vendor/` лежат сторонние библиотеки, их можно восстановить командой `composer install` по `composer.lock`, хранить их в git незачем. `.env` содержит секреты (пароль к базе), и их нельзя публиковать.

**Задание 8. Почему пакеты ставим вручную, а не через User data?**
User data выполняется только при первом запуске, а экземпляр у нас уже создан. Кроме того, ручная установка учит понимать каждый шаг и видеть ошибки сразу, а ошибку в User data найти сложнее (только в логе). В реальном проекте это можно автоматизировать, но на этом этапе важнее понимание.

**Задание 10. Почему пароль к БД в .env на сервере? Почему публичный репозиторий безопасен?**
Пароль в коде попал бы в историю git и стал виден всем, а сменить его пришлось бы переписыванием кода. В `.env` на сервере его читают только `ec2-user` и группа `apache`, а у каждого окружения может быть свой пароль. Публичный репозиторий безопасен, потому что в нём только код без секретов, а база слушает только localhost и закрыта от интернета.

**Задание 12. Что увидит посетитель во время git pull? Что будет, если после pull не выполнится composer install?**
Во время `git pull` файлы заменяются по одному, поэтому посетитель может на секунды получить смесь старых и новых файлов: сломанную страницу или ошибку. Если после pull не выполнится `composer install`, новый код может потребовать библиотеки, которых нет в `vendor/`, и сайт упадёт с ошибкой (например, `vendor/ is missing` или class not found).

**Задание 13. Почему /health отвечает ok, хотя главная страница не работает? Что он проверяет? Чего не хватает?**
`/health` проверяет только, что PHP-FPM работает и приложение может подключиться к базе. Он не рендерит шаблоны, поэтому синтаксическая ошибка в `views/layout.php` его не задевает. Такой проверке не хватает проверки реальных страниц, например запроса к главной странице и проверки кода ответа 200 и ожидаемого содержимого.

**Задание 13. Сколько времени сайт был сломан? Из чего сложилось? Как сократить?**
Сайт был сломан около <N> минут. Время сложилось из нескольких шагов: обнаружение ошибки, `git revert` и `git push` на компьютере, запуск `deploy.sh` по SSH. Сократить можно автоматическими проверками перед деплоем (тесты, линтер `php -l`), проверкой реальных страниц в `/health` и автоматическим откатом при провале проверки, а также деплоем через CI/CD.

## 5. Ответы на контрольные вопросы (устные)

**Как проходит запрос от браузера до базы данных?**
Браузер отправляет HTTP-запрос на порт 80 в nginx. Статические файлы nginx отдаёт сам, а запросы к страницам передаёт через unix-сокет `/run/php-fpm/www.sock` в PHP-FPM. PHP-FPM выполняет `public/index.php`, который обращается к PostgreSQL на localhost:5432. Готовый HTML возвращается через nginx в браузер.

**Почему сервер может скачивать код, но не отправлять изменения? Почему это правильно?**
Репозиторий публичный, и скачивать из него может любой по HTTPS без ключей, а для отправки (`git push`) GitHub требует аутентификацию, которой на сервере нет. Это правильно по принципу минимальных привилегий: если сервер взломают, злоумышленник не сможет изменить код в репозитории и распространить его дальше.

**Что будет с загруженными файлами при удалении экземпляра EC2? Как это связано с EBS?**
Файлы лежат в `storage/uploads` на корневом томе EBS, а по умолчанию он удаляется вместе с экземпляром (Delete on termination), поэтому файлы будут потеряны. При простой остановке (Stop) данные сохраняются. Для надёжного хранения нужен отдельный том или отдельный сервис хранения (например, S3).

**Что общего у deploy.sh с CI/CD? Чего не хватает?**
CI/CD делает то же самое: где-то запускается команда, которая берёт код из репозитория и выкладывает его на сервер, а потом выполняет установку зависимостей, миграции и перезапуск. Моему процессу не хватает автоматического запуска (при push), тестов и проверок перед деплоем, проверки результата после деплоя, автоматического отката и деплоя без простоя.
